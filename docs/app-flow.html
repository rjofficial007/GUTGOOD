01Application Overview

GutGood is an AI gut-health companion. Its defining principle is passive logging: the user never fills a form — chat messages and scans are parsed into structured meal/symptom rows automatically. Everything below is extracted from the repository at commit ee45f08, not from a template.

Architecture: Clean Architecture, feature-first. Each feature owns presentation / domain / data. Cross-feature communication goes through AppStateService ValueNotifiers rather than direct provider coupling — that is why the chat screen can trigger insight regeneration without importing the insights feature.
State management is Provider + ChangeNotifier, not Riverpod or BLoC. The brief asked for Riverpod/BLoC documentation; this file documents what the codebase actually uses so the diagrams stay truthful.

Two findings in this path. (1) checkAndConsume() is wrapped in try/catch that logs and proceeds on Firestore error — the quota gate fails open. (2) There is no App Check and CORS is *, so any account can call the proxy; combined with the client-writable isPremium flag this is an open relay to your OpenAI bill.

Passive logging — the product's core promise

The AI is instructed to emit tags inline. ProcessChatTagUseCase strips them from the visible text and writes structured rows, so the user never sees a form.

[MEAL]{"items":["pizza","beer"],"mealType":"dinner"}[/MEAL]
   -> FirestoreService.logMeal()  -> meal_logs/{id}
   -> NotificationService.schedulePostMealCheckIn()   // 1-2h later

[SYMPTOM]{"symptom":"bloating","severity":3}[/SYMPTOM]
   -> FirestoreService.logSymptom(lastMealId: <linked>)  -> symptom_logs/{id}

[SCAN]{...}[/SCAN]   -> saveToScanHistory()
[SWAPS]{...}[/SWAPS] -> rendered as swap cards, not persisted
Perf note from the source: markdown was re-parsed on every token, which caused frame jank. The fix is a throttled UI flush (chat_provider.dart:494) — tokens accumulate and the tree repaints on an interval.

10Authentication Flows

Anonymous-first. Guests get a real Firebase uid so their logs persist, then merge into a permanent account on sign-in.

scroll horizontally to follow the flow · +/− to zoom · ⛶ fullscreen

Guest → permanent merge (the hard case)

scroll horizontally to follow the flow · +/− to zoom · ⛶ fullscreen
Why this must be server-side: after the credential-already-in-use branch the client's session has already switched to the permanent account, so request.auth.uid no longer matches the anonymous subtree and every client-side read fails with PERMISSION_DENIED. The Admin SDK bypasses rules and the marker makes it idempotent.
Data loss: mergeSubcollection() uses .limit(500) on the source and the dedupe target with no pagination. A guest with more than 500 chat messages silently loses the remainder.

Firestore rules — the important parts

function isOwner(userId) {
  return request.auth != null && request.auth.uid == userId;
}

// Server-authoritative counters: closes the "reset your own quota" bypass
match /daily_usage/{docId} {
  allow read:  if isOwner(userId);
  allow write: if false;              // only aiProxy (Admin SDK) may write
}

// Idempotency markers cannot be forged by a client
match /merges/{anonUid} {
  allow read:  if isOwner(userId);
  allow write: if false;
}

// ...but premium is only SHAPE-validated, not authorised:
function isValidPremiumFields() {
  let premium = request.resource.data.get('isPremium', false);
  let status  = request.resource.data.get('subscriptionStatus', 'free');
  return premium is bool && status is string && status in ['free','premium']
      && (premium == false || status == 'premium');
}   // a tampered client can still write isPremium: true
Highest-severity finding. usage.ts → isPremiumUser() reads that client-written flag and returns limit: Number.MAX_SAFE_INTEGER. A modified client grants itself unlimited OpenAI spend on your account. Fix: RevenueCat webhook → Cloud Function → Admin SDK write, and set allow write: if false on those two fields.

22Offline Mode

Firestore's SDK owns write queuing; the app adds a global banner and a hard pre-send guard.

scroll horizontally to follow the flow · +/− to zoom · ⛶ fullscreen
Design choice worth knowing: chat send is rejected offline rather than queued (ChatSendError.offline). That is deliberate — an AI reply cannot be produced offline, so queuing would create a message that appears sent but never answers. Firestore writes (logs, profile edits) are queued and flush on reconnect.
